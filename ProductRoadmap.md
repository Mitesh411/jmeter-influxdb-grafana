# Product Roadmap: Performance Testing Framework

Last updated: 2026-11-08 · Branch: `Performance-testing-framework`

## 1. Where the product stands today

A local, Docker Compose based framework for load testing backend APIs and measuring frontend performance, with all results in Grafana.

| Component | What it does today |
|-----------|--------------------|
| **JMeter 5.6.3** | Runs `.jmx` plans headless (`jmeter/run-test.sh`). Two example plans: `blazedemo.jmx` (website flow) and `api-demo.jmx` (REST API against the local `demo-api`). Live metrics go to InfluxDB every 5 s. |
| **sitespeed.io 42.10** | Measures Core Web Vitals, visual metrics, page weight and the Coach score. A custom plugin (`sitespeed/plugins/influxdb`) writes each page load to InfluxDB. |
| **InfluxDB 1.12** | Single store for both tools. Every metric is tagged with `runId`. The `test_runs` measurement is a registry of all runs. |
| **Grafana 13** | Five provisioned dashboards: Performance overview (home), Backend (JMeter), Frontend (sitespeed.io), Run comparison, Request trace. |
| **Failure traces** | Every failed JMeter request is stored with its full request/response, assertion messages, timings and a W3C `traceparent` id. One click from a dashboard opens it. |
| **Jenkins LTS** | Configured as code. The `performance-test` job runs backend, frontend or both in parallel under one run id, gates on error %, and links to Grafana and the reports. |
| **Reports server** | nginx serves the JMeter HTML reports and sitespeed.io reports from `./results`. |

### Strengths
- **One place for all results.** Backend and frontend share a run id, so a single run can be viewed and compared as a whole.
- **Run comparison works across time.** Runs started at different times are overlaid on an elapsed-time axis, with Δ / Δ% per metric, per transaction and per page.
- **Request-level debugging.** A failure in a chart leads to the exact request and response, plus a trace id that an instrumented backend can be searched for.
- **Reproducible.** All image versions and Jenkins plugin versions are pinned, and Grafana, Jenkins and InfluxDB are provisioned as code.
- **Same path locally and in CI.** `docker compose run` and Jenkins call the same wrapper scripts.

### Weaknesses and risks
| # | Finding | Impact |
|---|---------|--------|
| W1 | The v1 work is not committed. README and CLAUDE.md describe only the old JMeter stack. `results/` (129 files) is tracked in git despite the new `.gitignore`. | New users cannot set the framework up. Risk of losing the work. |
| W2 | Failure traces store raw request headers and bodies. The BlazeDemo plan sends a (test) card number, and real APIs will send `Authorization` tokens and cookies. | Secrets or personal data could be stored in InfluxDB and shown in Grafana. |
| W3 | Dashboard JSON is generated by a script that lives outside the repo. The last request-trace layout fix was never regenerated. The frontend dashboard has not been visually checked. | Dashboards are hard to maintain, and a known display bug ships. |
| W4 | Backend percentiles are approximations: the mean of JMeter's sliding-window p95 values, not exact per-run values. | Comparisons can mislead on spiky runs. |
| W5 | Quality gates check only the JMeter error %. There are no latency SLOs and no frontend budgets. | Regressions pass CI unnoticed. |
| W6 | No data retention. InfluxDB, failure traces and sitespeed.io videos grow without limit. | The disk fills up, and queries slow down over months. |
| W7 | Local-only security model: InfluxDB has no auth, Grafana and Jenkins use admin/admin, and Jenkins has the Docker socket. | Unsafe to run on a shared or team server. |
| W8 | Single load generator, no tracing backend, no infrastructure metrics for the system under test. | Limits test scale and root-cause analysis. |
| W9 | No automated tests for the framework itself. | Changes to scripts or dashboards can break it silently. |
| W10 | InfluxDB 1.x is in maintenance mode. JMeter's built-in listener is tied to its write API. | A long-term platform risk. |

## 2. How items are prioritized

- **Impact:** H = removes a blocker or risk, or delivers the core promise (trustworthy results, catching regressions). M = clear workflow gain. L = nice to have.
- **Feasibility:** effort, plus how far the item depends on other work.
- **Order:** finish and secure v1 → make the results trustworthy and enforceable → scale and integrate → AI-assisted analysis.
- **Estimates:** hours for one engineer who knows the stack. Development includes documentation. Testing covers manual verification plus automated checks. Expect ±30 % accuracy. Rough conversion: 1 story point ≈ 4 h.

### Recommended next five items
1. **P0-4 + P0-1:** commit the work and document it. Nothing else matters if the work is lost or nobody can set it up.
2. **P0-5 redaction:** close the data-exposure risk before the framework is pointed at real APIs.
3. **P0-2 / P0-3:** fix the request-trace layout and make dashboards maintainable.
4. **P0-6 smoke test:** a safety net for everything that follows.
5. **P1-1 → P1-2 → P1-3:** exact statistics, then SLO gates, then automatic baselines. Together they turn the framework from "shows results" into "catches regressions".

### Success measures
- A new team member runs a first test and sees it in Grafana in under 15 minutes, using only the README.
- Every Jenkins run ends with an explicit pass/fail verdict against its SLOs and its baseline.
- From a failed request in a chart to the full request/response in 2 clicks or fewer (already met; keep it met).
- No secrets or personal data stored in failure traces (verified by a test in the P0-6 smoke suite).
- Disk use stays flat over months (retention, P1-6).

## 5. Assumptions and open questions
- **Scope:** a single team's local and CI use. Item P2-7 is needed only if the stack moves to a shared server.
- **Targets:** load tests point at test environments, never production. Public demo sites (BlazeDemo) stay at low load.
- **Open:** which chat tool to notify (Slack or Teams)? Which SLO numbers should be the defaults per application? Is sending redacted run data to an external LLM API (P3-1) acceptable under company data policy?
